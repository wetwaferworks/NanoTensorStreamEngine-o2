## Normalization Test C: fused reconstruction is bit-identical

bench/nq2-fused, q_proj [4096 x 3072], block 256, K 256 (results/
fused-testc-2026-11-24.txt). Path A materializes the tensor then
matvecs; path B matvecs directly from the packed form,
reconstructing each element inside the dot product.

- Output agreement: max abs diff 0.000e+00. Bit identical, because
  the accumulation order is unchanged. Fusion is numerically free.
- Isolated speed: A 245.0 M weights/s, B 200.1 M weights/s (fused
  about 18 percent slower per pass in this scalar bench; the
  reconstruction arithmetic rides inside the dot product).
- Memory: A holds 50.3 MB expanded; B holds 0.51 MB packed.
- The pipeline reading reverses the isolated one: in the real
  streaming path, A must ALSO pay the separate expansion pass
  (streamtest: 147 to 169 M weights/s), putting A's effective
  end-to-end rate near 93 M weights/s against B's 200. Fused wins
  where it matters, roughly 2x, at 1/100 the memory. Caveat: this
  bench's matvec is scalar with an fp64 accumulator; a SIMD
  production matmul moves both numbers and the book gather may
  vectorize worse. The bit-identity is the portable finding.

## Normalization research, Tests A+B: the lookup table is not promoted

JD relayed Gizmo's Normalization Research directive (rsqrt tests,
fused reconstruction, RMS frame precision) and directed work to
proceed on this bench as the baseline, with his laptop as the real
test platform and Cortana's queue noted. New bench: tools/
nq2-rsqrtbench.c (AMD EPYC 9D25, gcc -O3 -march=native; full
output in results/rsqrtbench-2026-11-24.txt).

Accuracy (relative error against the exact scalar reference, log
spread 1e-6 to 1e2): AVX-512 rsqrt14 has the best raw estimate
(5.8e-5 max); AVX2 rsqrt raw 2.6e-4; LUT1024 raw 2.4e-4; LUT256
raw 9.7e-4. One Newton step brings every method to fp32 grade
(2.2e-7 max or better). Accuracy is a solved problem for all of
them; the contest is speed, and it is not close:

- Block normalize, the real workload shape (256-wide row, one
  rsqrt per block): every method lands at 360 to 380 cycles per
  block, inside noise of each other. One rsqrt serves 256
  elements, so the method choice is unmeasurable end to end.
- Isolated throughput: hardware rsqrt is one to two orders of
  magnitude faster per value than the scalar table paths (the
  exact figure swings with bench contention; the ordering never
  does).

Verdict under the directive's own acceptance rule: the lookup
table does not outperform hardware rsqrt in matched end-to-end
measurements, so it is NOT promoted. Its home turf would be a
target with no rsqrt instruction. A second, quieter finding: any
approximate rsqrt in the engine's RMSNorm would change outputs in
the fourth decimal and break the anchor IDs, while buying no
measurable speed... so engine adoption is a fidelity decision for
JD, not a speed decision, and the exact path stays.
